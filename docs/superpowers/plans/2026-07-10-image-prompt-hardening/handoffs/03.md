## Contract delivered

### Content-based prompt currency

Prompt freshness is now content-based, not ID/version-based.
`prompt_assembly.prompt_is_current(prompt, panel, *, story_bible, project_dir,
prev_panel, config)` returns True iff:

1. `prompt.prompt_version >= IMAGE_PROMPT_VERSION`, AND
2. `prompt.planned_panel_id == panel.panel_id`, AND
3. `prompt.source_sha256 == compute_source_sha256(...)` — a fresh build from the
   current Story Bible + PlannedPanel + appearance state yields the same hash.

When `story_bible`/`project_dir`/`config` are not supplied, it falls back to the
legacy schema + panel-id identity check (used by tests that build prompts in
isolation). This is the single freshness function shared by the direct stage,
draw preflight, and single-panel rerender — all call
`ensure_current_panel_prompt`.

### Canonical source projection + `source_sha256`

`prompt_assembly.compute_source_sha256(config, project_dir, panel, story_bible,
prev_panel) -> str` hashes a sorted, stable JSON projection of every input the
canonical builder consumes:

- **PlannedPanel visual fields:** `panel_id`, `scene_id`, `panel_number`,
  `beat_ids`, `importance`, `shape_intent`, `crop_policy`, `generation_mode`,
  `shot_type`, `camera_angle`, `camera_note`, `background_description`,
  `lighting`, `mood`, `has_narration_caption`, `narration_mode`,
  `preferred_caption_zone`, `transition_in`, `transition_out`,
  `characters_present` (sorted), `character_actions`/`expressions`/`positions`
  (sorted list-of-pairs), `key_objects`, `visual_requirements`, `dialogue_text`,
  `sfx_text`, `aspect_preference`.
- **Prior-panel continuity inputs:** `prev_transition_out` + the previous
  panel's transition type, present characters, and their action/expression/
  position state (only for smooth-continuation / match-cut transitions, which
  is exactly what the builder synthesizes a continuity note for).
- **Referenced character records + appearance timelines:** `id`, `name`,
  `visual_anchor`, `default_outfit`, `distinguishing_features`,
  `appearance_states` (id/label/anchor/visually_significant/continuity_guard),
  `appearance_timeline` (state_id/scene_id/beat). Characters are filtered to
  those present in the panel and sorted by id.
- **Active location record + timeline:** the scene's location, projected the
  same way as a character.
- **Matched prop records:** recomputed via `_matched_prop_ids_for_panel` (same
  presence test the builder uses), projected as id/name/visual_anchor/
  first_appearance_scene.
- **Schema/version + language + config:** `IMAGE_PROMPT_VERSION`,
  `target_language` (`config.language_code()`), `continuity_mode`.

The hash is `sha256(json.dumps(projection, sort_keys=True, separators=(",",":")))`.
Deterministic regardless of Story Bible list/dict ordering.

**Excluded by design (per the brief):** active style text (changing style must
not rebuild stored panel structure — style is a generation-time input), and
reference file hashes (owned by Slice 04's `ReferencePlan`). The projection
never reads disk for reference images.

### State-aware overlay storage shape

User corrections are stored as overlays on `ImagePrompt.user_overlays`, separate
from the canonical IR. The overlay model:

```python
class PromptOverlayOp(BaseModel):
    field: OverlayField  # composition|setting|lighting|mood|constraints|
                         # continuity_note|action|expression|position
    value: str
    subject_character_id: str | None = None   # binds to one subject (never index)
    appearance_state_id: str | None = None    # None = state-neutral
    location_state_id: str | None = None      # binds to one location state
```

- **Subject-scoped ops** (`action`/`expression`/`position`) are keyed to
  `subject_character_id` + `appearance_state_id`. A state-neutral op
  (`appearance_state_id=None`) re-apes whenever the subject is present in any
  state. A state-specific op re-apes only when the subject's active state
  matches.
- **Panel-scoped ops** may carry `location_state_id` to bind to one location
  state (e.g. a setting correction authored in the pristine state).

### Rebuild API

`ensure_current_panel_prompt(config, project_dir, panel, story_bible, prev_panel)`
is the single rebuild entry point. On a stale prompt (hash mismatch or version
gap) it:

1. Recompiles canonical source → fresh `ImagePrompt`.
2. Stamps `fresh.source_sha256 = compute_source_sha256(...)`.
3. Reapplies `existing.user_overlays` via `reapply_overlays`, dropping
   incompatible ops with structured warnings (logged).
4. Persists the fresh prompt.

`prompt_assembly.reapply_overlays(prompt, overlays) -> list[OverlayWarning]`
replays ops in place and returns drop warnings. A successful reapply records
the surviving ops back onto `prompt.user_overlays`.

### Warning codes

| Code | When emitted |
|---|---|
| `subject_missing` | A subject-scoped op's `subject_character_id` is no longer present in the panel. |
| `state_incompatible` | A subject-scoped op was authored in a different appearance state than the subject's active state. |
| `location_state_incompatible` | A panel-scoped op bound to `location_state_id` does not match the panel's active location state. |
| `value_empty` | An overlay value is empty after trimming. |

### Overlay recording on edit

`panel_store.apply_prompt_patch` and `prompt_instructions.apply_instruction_patch`
now record overlay ops alongside applying the edit, so a later canonical rebuild
reapplies the correction:

- Panel-scoped edits record `PromptOverlayOp(field, value,
  location_state_id=prompt.location_state_id)`.
- Subject-scoped edits record `PromptOverlayOp(field, value,
  subject_character_id=<existing subject's id>,
  appearance_state_id=<existing subject's active state>)`.
- Repeated edits to the same field+entity+state supersede the older op
  (`_merge_overlays` dedups by `(field, subject_character_id,
  appearance_state_id, location_state_id)`).

### Prompt version

`IMAGE_PROMPT_VERSION = 22` (was 21). Old stored prompts are invalidated by the
version check and rebuilt on first access. Breaking stored prompt JSON is
acceptable per the plan.

## Behavior and deliberate deviations

- **Breaking stored prompt JSON:** `IMAGE_PROMPT_VERSION` bumped to 22. Old
  stored prompts (version 21) are rebuilt on first access. Acceptable per the
  plan.
- **Projection captures resolution inputs, not the resolved state:** the source
  hash covers the timeline entries + states + `beat_ids` that the appearance
  resolver consumes, rather than the resolved active state/identity itself.
  This is correct and deterministic: any input change that alters the resolved
  state also alters at least one projected input. Slice 04 can use the active
  state identities (stored on `PromptSubject.appearance_state_id` /
  `ImagePrompt.location_state_id`) independently.
- **`prompt_is_current` fallback:** when `story_bible`/`project_dir`/`config`
  are not supplied, the function performs only the legacy version + panel-id
  check. This keeps it usable by tests and callers that build prompts in
  isolation without a Story Bible. The three production callers (storyboard,
  draw, rerender) always supply the full inputs.
- **Overlay reappliation modifies the prompt's editable fields:** after a
  rebuild, overlays are applied to the fresh prompt's scene-direction fields
  (composition/setting/subject action/etc.), then `full_prompt`/`distilled` are
  NOT re-derived by `ensure_current_panel_prompt` (that happens downstream via
  `ensure_distilled_prompt` / `ensure_visual_brief` in the storyboard/draw
  stages). The `apply_prompt_patch` path does re-derive them (it owns that
  re-render). This matches the existing division of labor.
- No paid/model calls were made.
- No frontend files were touched (backend-only slice).
